# LXON testbed chains (725 / 726) — bring-up and teardown

**Disposable.** These are throwaway QBFT chains for testing the attested bridge against real
consensus. Nothing here is production, nothing here talks to production, and nothing here may be
pointed at production: chain 724 (`13.62.37.246` / `https://rpc.lxon.in`) is never a peer, never an
RPC target for a write, and never shares a key or a genesis with these files. The `keys/` material
in this directory is freshly generated for the testbed only.

All commands were run and every output below is measured, from `hyperledger/besu:26.10.0` on
OrbStack/Docker, 2026-10-22.

## Prerequisites

- OrbStack running: `orbctl status` → `Running` (else `orbctl start`).
- Image already cached (`docker images | grep besu` shows `hyperledger/besu:26.10.0`); no pull.
- **The local chain-724 mirror must be down.** `lxon-evm-node/docker-compose.yml` runs a sealer on
  the same host; two sealers on one box is a rule this testbed inherits from the plan, and Task 14
  asserts it. Check before any bring-up:

```console
$ docker ps -a --format '{{.Names}}\t{{.Status}}'
besu-cliq-test    Exited (2) 3 days ago
forktest          Exited (2) 3 days ago
$ lsof -iTCP -sTCP:LISTEN -P | grep -E ':(8545|8546|8555|8645|8646|8647|8648|8649|8665)\b' || echo "no port squabbles"
no port squabbles
```

- Disk is the binding resource, not RAM. `df -h /System/Volumes/Data` before starting anything;
  stop and report rather than continuing under 6 Gi free:

```console
$ df -h /System/Volumes/Data
/dev/disk3s5   228Gi   189Gi    12Gi    94%    2.6M  130M    2%   /System/Volumes/Data
```

## Bring-up (chain 725, four validators)

Ordering is not stylistic: an enode URL contains node-1's node id, and `--bootnodes` is parsed at
Besu startup, so the URL cannot be known — let alone valid — before node-1 has started. Also,
every service in `docker-compose.725.yml` interpolates `${BOOTNODE_1:?…}` when the file is *loaded*,
so **any** targeted `docker compose` command (even `up -d 725-node-1`, even `down`) needs the
variable set, or compose refuses to read the file:

```console
$ docker compose -f docker-compose.725.yml up -d 725-node-1
error while interpolating services.725-node-2.environment.BESU_BOOTNODES: required variable
BOOTNODE_1 is missing a value: run ./capture-enode.sh and export BOOTNODE_1 first
```

The three commands, in order, from this directory:

```bash
# 1. node-1 alone. It needs no BOOTNODE_1 at all -- it IS the root (BESU_IS_BOOTNODE=true).
docker compose -f docker-compose.725.yml up -d 725-node-1

# 2. capture node-1's real enode URL from its logs + its Docker address, and persist it
export BOOTNODE_1="$(./capture-enode.sh --save)"

# 3. the other three (node-5 stays behind the vote-in profile, so this starts exactly four)
docker compose -f docker-compose.725.yml up -d
```

Step 1 used to need a dummy value:

```console
$ docker compose -f docker-compose.725.yml up -d 725-node-1
error while interpolating services.725-node-2.environment.BESU_BOOTNODES: required variable
BOOTNODE_1 is missing a value: run ./capture-enode.sh and export BOOTNODE_1 first
```

That was Compose interpolating `${BOOTNODE_1:?…}` for **every** service at file load, including the
three you were not starting — so the variable was also required for `down`, `ps`, `logs` and
`stop`, which blocked tearing a running stack down on a host with nothing exported. Measured
2026-10-22: `down` failed with exactly that interpolation error while five containers were live.
The files now carry `${BOOTNODE_1:-}`, and the requirement moved to where the failure actually is —
the entrypoint refuses to start a non-root node with no bootnodes, because such a node does not
error on its own, it just sits at `peers=0` forever and looks like a consensus failure:

```console
$ docker compose -f docker-compose.725.yml up -d --no-deps 725-node-2   # BOOTNODE_1 unset
BOOTNODE ERROR: 725-node-2 is not the bootnode and BESU_BOOTNODES is empty.
  run ./capture-enode.sh, export BOOTNODE_1, then re-run up (see README bring-up).
```

Measured:

### What "healthy" means here, and what peers=3 takes

`net_peerCount` does not read 3 immediately: node-1 alone cannot seal (n=4 needs quorum 3), so
height stays `0x0` until three or more are up, and discovery keeps filling after that. Two real
measurements, and the spread is the point: Task 2's run reached `1 / 2 / 3 / 2` at ~50 s and
`3 / 3 / 3 / 3` at ~90 s from the last validator starting, while Task 2's reviewer, on a cold store
with nothing under `725/node-*`, found three of four RPCs still refusing to answer at T+95 s and the
mesh converged at **T+145-170 s**. Both are true; the second is the case that bites.

So do not judge topology on a timer. **Poll until it is true, with a budget** — and never let a
fixed sleep decide a consensus verdict, because `test-consensus.sh` reading height `-1` at 45 s
prints `FAIL port 8646 stalled at -1` about a perfectly healthy chain, and a false consensus
failure is worse than a slow one since it gets written into the runbook as a result:

```bash
for i in $(seq 1 30); do
  n=0
  for P in 8645 8646 8647 8648; do
    p=$(curl -s -m 3 "http://127.0.0.1:$P" -H 'content-type: application/json' \
        -d '{"jsonrpc":"2.0","id":1,"method":"net_peerCount","params":[]}' \
        | python3 -c 'import sys,json;print(int(json.load(sys.stdin)["result"],16))' 2>/dev/null || echo -1)
    [[ "$p" == "3" ]] && n=$((n+1))
  done
  echo "attempt $i: $n/4 at peers=3"; [[ $n -eq 4 ]] && break; sleep 10
done
```

## Bring-up (chain 726, one validator)

726 is a single validator with no peers, so it needs no bootnode, no `BOOTNODE_1`, and no pinned
subnet — it lets Docker auto-allocate and nothing about its identity depends on the address. It uses
the same `entrypoint-testnet-node.sh` and the same `perms` sidecar pattern, because the uid-1000 data
dir requirement that made the production sealer key work applies here too: a `726/node-1` owned by
your host uid crash-loops with a permission error that looks exactly like a consensus failure.

```bash
orbctl start                                   # the socket is not always up
docker compose -f docker-compose.726.yml up -d
# both chains together, which is the state Tasks 11-13 need:
docker compose -f docker-compose.725.yml up -d && docker compose -f docker-compose.726.yml up -d
```

The proof it is really 726 and not 725 wearing a hat, measured 2026-10-22 with both chains sealing:

```
port 8645 chainId=725 peers=3   ... 8648 chainId=725 peers=3
port 8665 chainId=726 peers=0            <- n=1: zero peers is correct, not a failure
725  838 -> 843 over 25 s   726  612 -> 621 over 25 s   (3 s blocks on both)
726 authored ONLY by 0xe8ea29ac…d2272 (node-6) over 9 consecutive blocks
725 authors over 4 blocks  = the four validators from validators-725.txt, one each
```

The author check is the cross-key proof: if a 725 key ever sealed on 726 the two chains would share
a signer, and two sealers with the same key and genesis fork a chain. `peers=0` on 726 is expected —
do not treat it as a broken node.

### The roster is five, and only four nodes run — read this before killing anything

`qbft_getValidatorsByBlockNumber("latest")` on 725 returns **five** addresses today: the four
genesis validators plus `0xd6f0ad29541a048bcf824afcc9ad8b6c2d17436f`, the spare Task 3 voted in. The
vote persists in QBFT's contract state and survives container restarts and `down` without `-v`; only
`down -v` (a fresh store) discards it. So the chain currently running has n=5, quorum 4, f=1 — and
only four of its validators are actually up. **That means the stack is sitting at exactly its quorum
minimum: stopping any one of the four running containers halts 725**, which is the opposite of the
"kill one, it keeps sealing" result Task 3 measured when the roster was four.

Two ways to fix the fragility before the long Tasks 11-13, and pick one deliberately rather than by
accident: start the fifth validator too (`--profile vote-in up -d --no-deps 725-node-5`, giving 5 of 5
up and real f=1 headroom), or `down -v` and bring up a clean four. The first keeps the M1 history; the
second makes the topology match the docs. Either way, do not run Tasks 11-13 against four-of-five
without deciding which of the two states you are in.

## Memory: the caps hold, with headroom to spare

`JAVA_OPTS` caps the heap (`-Xmx320m`, `-XX:MaxRAM=480m`); `mem_limit`/`memswap_limit` cap the whole
container including off-heap, which is what matters with four JVMs on a host with ~4 GiB
reclaimable. There is **no `--Xmx` passed to Besu** — Besu has no such option and picocli aborts the
node with `Unknown option: '--Xmx=320m'`, so JVM memory must come from `JAVA_OPTS` only.

```console
$ docker stats --no-stream --format '{{.Name}}\t{{.MemUsage}}\t{{.CPUPerc}}' | grep lxon-725
lxon-725-node-4    337.9MiB / 512MiB   1.25%
lxon-725-node-3    351.5MiB / 512MiB   1.25%
lxon-725-node-2    351.5MiB / 512MiB   2.11%
lxon-725-node-1    361.4MiB / 512MiB   7.90%
```

Worst container 361.4 MiB of 512 MiB (71 %). No container was OOM-killed:
`docker inspect --format '{{.Name}} restarts={{.RestartCount}} oom={{.State.OOMKilled}}'` reported
`restarts=0 oom=false` for all four. Task 5 therefore does **not** need its memory fallbacks.
Re-measured 2026-10-22 with **both** chains up (the state Tasks 11-13 need), which is five JVMs on
this host instead of four:

```console

lxon-725-node-3    396.5MiB / 512MiB   14.67%
lxon-725-node-1    395.9MiB / 512MiB   7.39%
lxon-725-node-2    385.3MiB / 512MiB   2.61%
```

Worst container 396.5 MiB of 512 MiB (77 %), up from 361.4 MiB (71 %) at four containers — so a
near-empty chain grows ~35 MiB per node once a second chain is sealing alongside it. Still
`restarts=0 oom=false` on all five. The aggregate is ~1.9 GiB against ~4 GiB reclaimable, and adding
the fifth 725 validator (the `vote-in` profile) would put it near 2.3 GiB. **Headroom is real but no
longer generous**: if Tasks 11-13 need more, the answer is spec §4.5's fallback — replace 726 with an
anvil block — *before* raising any heap, because raising `-Xmx` above the `mem_limit` converts a
memory problem into an OOM kill.

For the record on how this was evidenced, not just what was measured: during the four-container run
`docker events --since 3600s --until <now>` listed only `exec_*` health-check events for these
containers (OrbStack surfaced no `die`/`kill`, but also no `create`/`start`, so treat the
`docker inspect` counters, not the event stream, as the OOM evidence).


## Teardown

```bash
BOOTNODE_1="$(cat enode-1.txt)" docker compose -f docker-compose.725.yml down -v
docker ps --format '{{.Names}}' | grep lxon-725 || echo "725 fully stopped"
```

```console
$ BOOTNODE_1="$(cat enode-1.txt)" docker compose -f docker-compose.725.yml down -v
 ... Container lxon-725-node-{1..4} Removed
 Network lxon-testnet-725_default Removed
$ docker ps --format '{{.Names}}' | grep lxon-725 || echo "725 fully stopped"
725 fully stopped
```

Data dirs are bind mounts, not named volumes, so `down -v` keeps them: the chain resumes from its
recorded height on the next `up` instead of re-bootstrapping. Remove them (`rm -rf 725/node-*`)
when a fresh chain is wanted — e.g. after a genesis change, where a stale data dir fails as a
genesis-hash mismatch rather than as an obvious error.

`enode-1.txt` survives the teardown unchanged: node-1's id comes from `keys/node-1.hex` (passed as
`--node-private-key-file`) and its address is pinned to `172.28.97.2`, so Task 3 and Task 5 can use
the file as-is. Proven, not assumed — after a full `down -v` the stack was brought up again with
`BOOTNODE_1="$(cat enode-1.txt)"` and nothing recaptured, and it reached `peers=3` on all four with
heights advancing in lockstep (181 → 186).

## If it does not come up

Three failure modes were actually hit, in this order:

1. **`Argument is too large to represent a UInt256`, node crash-loops at exit 2.** An `alloc`
   balance exceeds 64 hex digits. Fixed in `834f454`; the production value is `0x1337` + 60 zeros
   = 32 bytes exactly.
2. **`Invalid bootnode: '...@lxon-725-node-1:30303'. ... Invalid ip address.`**, exit 2, every peer
   crash-loops. This is why `capture-enode.sh` emits an **IPv4 literal**: Besu validates the host of
   a bootnode enode URL as an IP address and rejects a DNS name, even though Docker's embedded DNS
   resolves container names on the compose network. Besu's own log line shows `@127.0.0.1:30303`,
   which is node-1's local view and useless to a peer — the script substitutes the address Docker
   actually assigned, read from `docker inspect`.
3. **`Failed to create data directory`** — the `perms` service did not complete, so `725/node-N` is
   not uid-1000 owned. Re-run it: `docker compose -f docker-compose.725.yml up perms`. And an empty
   validator list in `extraData` (a genesis whose `blockchain.nodes.keys` were not filled in) seals
   forever nothing: check with `qbft_getValidatorsByBlockNumber ["0x0"]` returning four addresses.

Height staying `0x0` while only node-1 runs is *not* a fault — 4 validators with `requesttimeout`
quorum 3 cannot seal a block on one node.
